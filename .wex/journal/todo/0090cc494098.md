# A form handled by two processors must not fail the build

Opened: 2026-11-09
Updated: 2026-11-09
Author: agent:main

`FormProcessorRegistryPass` (commit `1ca588e`) refused any form claimed by two processors. Syrtis
(`local/api`) does it on purpose: `ModelReplaceForm`, not ajax, posted to its own page, handled
by `ModelReplaceFormProcessor` on one route and `ModelReplaceDeleteFormProcessor` on another,
each picked by `#[EntityFormProcessor]` on its controller method. No lookup by name or by form
class is involved, so nothing is ambiguous — and its container no longer builds.

## Task

Keep the build error for a processor that cannot name its form class. Move the "two processors"
check to the lookup: the registry keeps every processor of a form, and a lookup by name or by
form class that lands on one with several throws, naming them — that form only, only when asked.

## Done

- `FormProcessorRegistryPass` keeps every processor of a form (`form → list of service ids`);
  only a processor unable to name its form class still fails the build.
- `FormProcessorRegistry::findByFormName()` / `findByFormClass()` throw
  `Wexample\SymfonyForms\Exception\AmbiguousFormProcessorException` for a form with several
  processors, naming them and the two ways out — that form only, only when looked up.
- Tests: the pass keeps both processors of a shared form; `tests/Unit/FormProcessorRegistryTest.php`
  (one processor found, none for an unknown form, the shared one refused, the others untouched).
  103 tests green.
- Checked on Syrtis: `php bin/console cache:clear` in `api_local_symfony`, which mounts this
  package from `vendor-dev`, succeeds again.
