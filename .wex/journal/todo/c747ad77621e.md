# Read-only fields in an edit form

Opened: 2026-10-01
Updated: 2026-10-01
Author: agent:main

Answering the Sapiens checklist line «Read-only fields inside an edit form (creation date and the like)»
(`HOME_HABILIS/local/sapiens/.wex/knowledge/contributing/stack-requirements.md.j2`), under
`PACKAGES/PHP/.wex/tmp/capability-checklist-protocol.md`.

## Verdict

Real gap, implemented. Two distinct needs, as the application agent says, and both are now in
the package. What is left is a version bump and publication, which belong to whoever publishes.

## Where the application agent's detail was wrong

Its premise is inverted. No widget of `assets/form/form_theme.html.twig` forwarded `disabled`,
`readonly` or `attr`: the blocks called `component()` with an explicit map (`name, id, label,
placeholder, required, value`). So `disabled: true` rendered a field that **looked and behaved
editable**, and the typed value was dropped in silence — worse than grey, which was the risk
it warned against. The grey-disabled problem it describes did not exist here.

Right on everything else: `readonly` alone is decoration, `disabled` is the server-side
guarantee, HTML has no `readonly` for a select, a radio group or a checkbox.

## What was built

- `assets/form/form_theme.html.twig`
  - `wex_frozen_attributes`: `readonly aria-readonly="true"` on a frozen field, never the HTML
    `disabled` — focusable, read by a screen reader, not said to be unavailable.
  - `required` dropped when frozen: a frozen empty required field would have made the browser
    refuse every submission of the form. Found while writing the tests.
  - `wex_frozen_value_widget` + `wex_frozen_choice_label` for the controls HTML cannot freeze
    (select, radio, switch, file, otp, emoji): the value they hold, in a readonly field with
    **no `name`**, so nothing of them is submitted at all.
  - `display_value_widget`.
- `src/Form/Type/DisplayValueType.php`: `mapped: false`, `required: false`, `disabled: true`.
  Renders a label and a value, an em-dash when empty, no element a browser submits. The value
  arrives formatted — UTC to the reader's timezone is a question about the reader, which the
  field does not know.
- No new API for the conditional, against the detail's suggestion: `disabled` is already a
  per-field Symfony option decided in `buildForm`, and a `frozen_fields` list or callable would
  be a second way of saying it with no second guarantee. The same form class serving two roles
  is shown in the fixture and written up in the cookbook.
- No bundle option: there was no behaviour to preserve, since nothing was rendered before.

## Divergences and leaks, for the record

- The `.vue.twig` components take a `disabled` prop but the Symfony form theme only ever
  renders `html.twig` (`component()` of `symfony-loader`), so nothing is silently lost on the
  Vue side. If a Vue form is ever wired, `readonly` there is a `symfony-design-system` line.
- A frozen `readonly` input *is* submitted by the browser. That is intended: the refusal is
  Symfony ignoring the submitted value, and the test posts for every field to prove it.
- A frozen switch reads `field.<name>.choice.{1,0}.label` in the form's domain, the convention
  `SelectInputType` and `RadioInputType` already use. `@form::` resolves inside the form
  component, where `symfony-loader`'s `FormService` pushes the domain. Missing keys show the
  key, which is visible and says what to write.
- `.form--group--display` has no style yet: `symfony-design-system` owns the scss, and the
  class is the seam.

## Test infrastructure, which the package had none of

`phpunit.xml`, `tests/bootstrap.php`, `tests/Fixtures/App/AppKernel.php`, a `Record` model and
a `RecordForm` with one field per shipped type. 12 tests, 155 assertions.

No php on the host: `docker run --rm -v <packages>:/pkgs -w /pkgs/symfony-forms wex-php85-intl`,
an image built from `php:8.5-cli` plus `intl` and `zip` (`wexample/php-date` requires `ext-intl`
and neither `php:8.5-cli` nor the quality image carries it; `wex-php-roave` has intl on 8.4).
`wex app::test/run` cannot work here — it calls `vendor/bin/phpunit` with the host php.

Checked by rendering through the real pipeline — a `RenderPass` from
`AdaptiveRendererService::createRenderPass()`, a layout node, the design-system components —
**not** over HTTP in a running app, which this host cannot do.

## Found on the way, outside this line

- `symfony/form` was missing from `require` although every form type extends
  `Symfony\Component\Form\AbstractType`. Added, `^7.4 || ^8.0`. It worked only because every
  installing application brings it.
- `symfony-loader` and `symfony-routing` raise 7 implicit-nullable deprecations on PHP 8.5, so
  `failOnDeprecation` cannot be held green from here. Their own agents' line.
- `AdaptiveRendererService::createRenderPass()` fatals without a current request and without the
  `_adaptive_output_type` / `_adaptive_layout_base` request attributes — it passes `null` into
  non-nullable setters rather than defaulting. `symfony-loader`'s line.
- `symfony-helpers` needs `symfony/security-core` for `ReversedRoleHierarchy`; carried here as a
  `require-dev` rather than patching a sibling package.
